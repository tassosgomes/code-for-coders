## Revisão semântica (focused)

- **Audit `getAuditRecordInternal`** (`Api/Endpoints/AuditRecordEndpoints.cs:48-89`)
  - Faz a mesma validação local de JWT que o search: tenant/sessão → 401 `TOKEN_INVALID`; escopo e papel `administrador` → 403.
  - `AuditRecordDetailQueries` filtra por `TenantId` + `Id` + `RecordType == original`. Assim, ID inexistente, ID de outro tenant e ID de complemento devolvem `null`, que vira o mesmo 404 `AUDIT_RECORD_NOT_FOUND`.
  - Os complementos são ordenados por `ConfirmedAt` e depois por `Id`, e a leitura usa `AsNoTracking`.
  - O search passou a excluir complementos (`AuditRecordSearchQueries.cs:35,43`).
  - Atributos: o `complemento` persistido é sempre um mapa string→string, já validado na ingestão, ou `null` quando é `complemento-invalido`. Por isso a desserialização em `GetAuditRecord.cs` é segura.
  - Os testes cobrem: valores como recebidos, ausências preservadas com razões, inexistente, outro tenant, ID de complemento, ordenação com empate de momento e leitura sem alterar linhas.
- **Persistência**
  - A migration foi gerada por EF: há `.Designer.cs` e snapshot atualizado.
  - Um `record_type` com check constraints e uma FK composta `(tenant_id, original_record_id) → (tenant_id, id)` impedem complemento cruzado entre tenants.
  - Há índice único `(tenant_id, confirmation_id)`.
  - A trigger append-only e as permissões continuam inalteradas.
