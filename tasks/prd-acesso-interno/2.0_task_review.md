## Conferência semântica

- **Provisionamento:** `StaffProvisioningCommand` entra antes do `WebApplication` da API e resolve o caso de uso em escopo com tenant. O caso de uso grava num commit: conta `InternalActor` confirmada sem credencial, papel `administrador`, token com hash SHA-256 e pedido `recuperacao-de-senha` protegido no outbox. Em tenant que já tem administrador, sai com 0 sem alterar nada. E-mail de aluno ou de outra conta interna sai com 1. Os logs trazem só tenant e data; o console não mostra e-mail, link nem segredo. Os testes verificam que nenhum `auditoria.ato-praticado.v1` foi gravado (RN-25/RN-A12).
- **Modelo:** `StaffRoleAssignment` tem índice único `(tenant_id, account_id, role)`. `StaffRoleCatalog` é fixo em código (DP-03). `StaffSession` tem FK composta por tenant e query filters por tenant.
- **Redefinição interna:** `POST /internal/v1/staff-password-resets` exige asserção com escopo `staff-passwords:reset`. O escopo está registrado para o emissor `bff-admin` (1.0). O caso de uso aceita só token `recuperacao-de-senha` de conta `InternalActor` ativa e aplica `StudentPasswordPolicy` (política CAP-001). Ele cria a credencial quando ela ainda não existe, revoga as `StaffSession` e consome todos os tokens pendentes num commit, com idempotência de 24 h. O caminho de aluno (`FindStudentAccountAsync`) continua filtrando `AccountType.Student`, então um token interno não serve no fluxo de aluno. Os erros saem como 422 `RESET_TOKEN_INVALID`/`PASSWORD_POLICY_VIOLATION`/`IDEMPOTENCY_CONFLICT`, conforme `internal-api-contract.yaml`.
- **BFF:** `POST /api/v1/staff-password-resets` segue o `api-contract.yaml` (`resetStaffPassword`, servidor `/api/v1`) e mapeia `IDEMPOTENCY_CONFLICT` → `IDEMPOTENCY_KEY_REUSED`. O cliente tipado usa resiliência padrão sem retry em POST. `ServiceAssertionTokenFactory` emite `iss/sub=bff-admin`, `aud=identity-internal`, escopo e `kid`. O E2E confere a assinatura RSA do token enviado, o que exercita o adaptador real sobre transporte falso. O CSRF fica dispensado só para esse POST anônimo, que o contrato declara `security: []`.
- **R3 da 1.0 consumida:** `StaffIdentityOptions` lê exatamente a seção `StaffIdentity__*` que o Compose já injetava no `bff-admin`, com `ValidateOnStart`.
- **Compose/docs:** Identity recebe `StaffAccount__PasswordResetBaseUrl`/`LifetimeHours`. A doc local descreve `ef database update` e o comando `provision-first-admin`.
- **nginx do SPA:** `/api/v1/` → `bff-admin`. O `log_format` registra o caminho sem query string, então o token fica fora do access log.
- **SPA:** a rota `/redefinir-senha` (basename `/admin`) lê o token uma vez e o remove do histórico com `replaceState` em `useLayoutEffect`. A página envia `{token,newPassword}` no corpo com `Idempotency-Key`, mostra o sucesso e dá o link para `/entrar`. `api-client.ts` não precisou mudar: `API_URL=http://localhost:8081` + caminho `/api/v1/...` passa pelo nginx.
- **Dependências novas do admin-spa:** `react-hook-form` e `@hookform/resolvers`. As duas são o padrão de formulários da skill `react` (RHF + zod) e já estão no student-spa; nenhuma dependência inesperada.
