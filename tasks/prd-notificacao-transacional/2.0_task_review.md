## Verificação semântica

- **Recusa antes de qualquer renderização/chamada ao provedor:** `AcceptNotificationSendRequest.cs`
  calcula `NotificationSendRequestRules.GetRefusalReason` logo após a validação de forma e, se não
  nulo, grava `DeliveryRecord.CreateRefused` e retorna — nenhum código do `DeliverAcceptedNotification`
  (renderização, `ITransactionalEmailSender`) é alcançado nesse caminho. Confirmado por teste
  (`Assert.Empty(emailSender.SentEmails)` após 250ms de espera, nos 3 cenários).
- **Três motivos diferenciáveis:** `NotificationRefusalReasons.MissingPurpose` ("finalidade ausente"),
  `UnknownModel` ("modelo desconhecido"), `MissingData` ("dado faltante") — persistidos em
  `DeliveryRecord.Reason` e verificados nos 3 testes via `Assert.Equal(expectedReason, ...)`.
- **`ack`, nunca `nack`, para recusa de negócio:** a recusa não lança exceção — o caso de uso retorna
  normalmente e `NotificationSendRequestConsumerWorker` segue o caminho de sucesso
  (`BasicAckAsync`). O `nack(requeue:false)` continua reservado para payload malformado
  (`JsonException`, envelope inválido), sem sobreposição com o caminho de recusa de negócio — a
  decisão fechada da task foi respeitada.
- **Nenhum outbox de `mensagem-entregue` gravado:** verificado nos 3 testes via consulta a
  `OutboxMessages` filtrando `notificacao.mensagem-entregue.v1`.
- **Modelo de domínio:** `DeliveryRecord.CreateRefused` valida identidade/destinatário/motivo como
  obrigatórios e os demais campos (nome, link, finalidade, modelo) como opcionais — coerente com um
  pedido recusado por finalidade ausente, por exemplo, não ter `modelo` avaliável. `DeliveryRecord.Create`
  (caminho aceito) preserva a obrigatoriedade original desses campos; os operadores `!` introduzidos em
  `DeliverAcceptedNotification.cs` são seguros porque só operam sobre registros com `Status =
  Accepted`, cuja obrigatoriedade é garantida por `ValidateRequiredText` em `Create`.
- **Migration:** `AlterColumn` torna `recipient_name`, `purpose`, `model`, `link`, `accepted_on`
  opcionais e adiciona `reason`/`refused_on`; `ModelSnapshot` foi regenerado de forma consistente.
  `Down` reverte com `defaultValue` para as colunas voltando a `NOT NULL` — padrão aceitável para
  rollback de migration em ambiente ainda não produtivo desta fatia.
- **Fora do escopo respeitado:** nenhum teste ou código cobre payload malformado (V-01/nack),
  idempotência (V-03) ou `recuperacao-de-senha` (V-04); os 3 cenários usam
  `finalidade: confirmacao-de-conta`, como determinado pela task.
